# OPS-003 — Approve or reject a queued task

**Owner:** SAC-007  
**Actors:** Approver (floor lead / estimator lead; lab uses `X-Actor-Id` / dev-operator)  
**Goal:** Human gate for high-risk work — nothing “just runs” when policy says someone must sign off.

## Flow

1. Ensure a task exists in **`needs_approval`** (create a high-risk / commit-mode task from Console, or seed one in the lab).  
2. Open **Tasks** (`/tasks`). Filter by state if needed; open the task detail.  
3. Review intent, payloads, and any prior dry-run evidence on the record.  
4. Choose **Approve** or **Reject**.  
5. Confirm state updates (`completed` or `rejected`) and that **approved_by** / **approved_at** (or equivalent audit fields) are set.  
6. Optional: use the task’s `correlation_id` in **Logs** to confirm the action was recorded in the structured trail.

## Success

- Only `needs_approval` tasks accept approve/reject; other states stay unchanged.  
- State and actor audit are visible on the task detail.  
- Reject does not call the ERP. Approve in current product still does **not** perform a live ERP commit (commit deferred — evidence may note that).  

## Failure / degraded

- Wrong state → API/UI refuses the action with a clear message.  
- Missing actor header in lab → default dev actor still leaves an audit name; production SSO is out of scope for this scenario.

## System notes

- APIs: `GET /tasks`, `GET /tasks/:id`, `POST /tasks/:id/approve`, `POST /tasks/:id/reject`  
- Screens: `/tasks`, `/tasks/[id]`
