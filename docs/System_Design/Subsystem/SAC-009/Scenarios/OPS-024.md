## Goal

A customer (or many shops) uses **Offer A (SaaS multi-tenant)** on a **shared** control-plane platform. Multi-tenant features are **in the SKU**: tenant context, isolation (when built), and (later) tenant admin / metering. Pricing is **subscription / SaaS**, not dedicated-only license.

## Actors

- Platform operator (vendor)  
- Tenant admin / shop operator (per manufacturer)

## Preconditions

- Platform deployed with `DEPLOYMENT_MODE=multi_tenant`  
- Tenants provisioned (process may be services-led until productized — RISK-04)  
- Actor authenticated into a tenant context (future auth; stub headers today)

## Main flow

1. Operator works in tenant A context (`X-Tenant-Id` or session).  
2. Ontology + AI and skills run scoped to tenant A.  
3. Platform (when built) can list / switch tenants for entitled platform roles.  
4. Tenant B data is not visible to tenant A actors.

## Alternate / exception

- Missing tenant context → fail closed or use documented fallback only for platform ops.  
- Cross-tenant access attempt → deny + evidence in logs (when isolation ships).

## Acceptance (for later TR)

- Mode `multi_tenant` on config API  
- Documented SaaS SKU includes multi-tenant feature family  
- Isolation evidence per TP-OPS-024 (row-level / schema policy when implemented)  
- Scenarios stay **Open** until TR + SRVM

## Notes

**Do not build full SaaS isolation in this docs pass.** Env + request tenant resolution may exist as stubs; GAP-13 tracks partitioned CP data and admin UI.
