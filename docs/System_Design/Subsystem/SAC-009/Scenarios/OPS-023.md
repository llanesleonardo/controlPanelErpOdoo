## Goal

A customer buys **Offer B (dedicated / single-tenant)**. They deploy or receive a stack with `DEPLOYMENT_MODE=single_tenant`. They use the full Ontology + AI manufacturing hub for **their** plant. They **cannot** access multi-tenant SaaS features (tenant picker, other tenants, platform multi-shop admin). Pricing reflects dedicated SKU — not SaaS subscription seats alone.

## Actors

- Plant admin / integrator  
- Operator (estimator, floor lead)

## Preconditions

- Entitlement / mode is **dedicated** (`single_tenant`)  
- `TENANT_ID` and `DEPLOYMENT_PROFILE` set for that customer  
- Ontology + peers configured for that plant (rebind as needed)

## Main flow

1. Operator opens Ontology + AI surfaces (Schema, Explorer, sections).  
2. System resolves tenant only from deployment env (`TENANT_ID`).  
3. Multi-tenant UI/API entry points are **absent or rejected** (when entitlement gates exist).  
4. Work proceeds on allowlisted skills for this plant only.

## Alternate / exception

- Client sends `X-Tenant-Id` for another slug → ignored or rejected (single-tenant policy).  
- Attempt to open SaaS tenant-admin → not available under this SKU.

## Acceptance (for later TR)

- Documented mode + pricing SKU for Offer B  
- Config shows `mode=single_tenant` (`GET /config/deployment`)  
- No multi-tenant admin path in this deployment (when feature gates ship)  
- Evidence: TP-OPS-023 report

## Notes

**Specified ahead of full code.** Env stub may already expose mode; entitlement UI/API gates and license checks are **future build**, not required to keep this scenario Open.
